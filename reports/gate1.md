# Gate 1 assessment (data feasibility)

Numbers below are copied from `reports/spike.md` (generated by script). Source: CodeNet metadata, Accepted vs Time Limit Exceeded, C++/Java/Python.

## Verdict: PASS, with a scope change (AtCoder only)

### Finding 1 - AIZU labels are not trustworthy; AtCoder labels are clean
| dataset | lang | AC rows with cpu_time >= 1.0x limit |
|---|---|---|
| AtCoder | C++ / Java / Python | 0.00% / 0.01% / 0.01% |
| AIZU | C++ / Java / Python | 0.02% / 2.52% / 7.18% |

AIZU Python TLE rows are ALL > 3x the stated limit, and 7.18% of AIZU Python AC rows exceed the stated limit.
So AIZU's per-problem `time_limit` does not apply uniformly across languages (the plan assumed it would).
AtCoder TLE cpu_time clusters just above the limit (censored, as expected), AC does not exceed it.

### Finding 2 - Statements are only usable for AtCoder
| dataset | problems | Constraints section | numeric bound found (crude regex) | contains Japanese |
|---|---|---|---|---|
| AtCoder | 1519 | 1502 | 1432 | 4 |
| AIZU | 2534 | 552 | 476 | 1352 |

Kill criterion was "< ~60% parseable -> constraints optional". AtCoder: 94.3% (1432/1519) passes; AIZU: 18.8% (476/2534) fails.

### Finding 3 - Shrink criteria on AtCoder alone (>= ~1,500 TLE submissions and >= ~150 problems with TLE per language)
| lang | TLE submissions | problems with TLE | problems with both AC and TLE | both, >= 5 each |
|---|---|---|---|---|
| C++ | 275,834 | 1467 | 1467 | 1321 |
| Java | 29,714 | 966 | 958 | 615 |
| Python | 290,842 | 1171 | 1149 | 870 |

All three languages pass with large margins. A 20% problem-disjoint test split leaves roughly 190 Java problems with TLE (estimate; verified when splits are built). No need to drop to 2 languages.

### Finding 4 - Python needs a runtime distinction
AtCoder Python TLE: 210,457 CPython vs 80,385 PyPy (`original_language` contains "PyPy"). Speeds differ by an order of magnitude, so runtime (cpython / pypy) becomes an explicit input token and the sandbox needs both interpreters.

### Finding 5 - Borderline-AC rule is cheap
Dropping AC rows with cpu_time >= 0.8x limit removes 0.37% (C++), 1.19% (Java), 1.28% (Python) of AtCoder AC rows. Keep as default, report threshold ablation.

## Recommended decisions for Gate 1 approval
1. Primary dataset = AtCoder only (1,519 problems). AIZU is excluded from training and evaluation. Possible later use: an out-of-distribution robustness check with its caveats stated in the README.
2. Keep all 3 languages; add runtime token for Python (CPython vs PyPy).
3. Next extraction pass (about 10 min, ~1 GB): only AtCoder problems with both AC and TLE in a language, capped per problem/language/user (proposal: up to 40 AC + 40 TLE per problem per language, one per user first).
4. Base-model choice still deferred to the start of Phase 3.

## Caveats (stated, not hidden)
- The statement probe is a crude regex indicator, not the Phase 2 parser; real accuracy will be measured on 150 hand-labelled problems.
- Time limits are from `problem_list.csv`; on AtCoder they appear consistent across languages (AC essentially never exceeds them), but rejudging variance is not measured.
- TLE labels reflect AtCoder's judge at submission time, not our M2/Colima hardware.
